## 1. 목표와 검토 범위

우리는 Shopshorts, Hanmadi App/Admin, Festa, 블로그, Replay와 공용 LiteLLM에서 문맥·의미 판단이 필요한 부분에 JEV를 활용하려고 해.

- JEV로 대체할 기존 LLM 판단과, 새로 추가하는 검수가 구분돼 있는가?
- 생성 전에 필요한 정보·후속 질문 방향을 판단해 불필요한 생성을 줄이는가?
- 생성 후에만 확인할 수 있는 오류를 적절히 검수하는가?
- JEV 뒤에 기존 LLM을 다시 호출하면서 비용·지연만 늘어나는 부분은 없는가?
- 규칙으로 확정할 수 있는 계산·권한·쿼터·상태 전이와 사람 승인은 유지되는가?

## 3. 마지막 검증 기록상 상태

일반 판단 경로:

```text
앱 서버 → 공통 JEV SDK → LiteLLM → TypeSafe
```

공통 추천 경로:

```text
앱/워커 → topic-discovery → 공식 검색·조사
→ 연결된 Codex/Claude 계정으로 초안 생성
→ JEV 판단 → 필요시 native LLM 재검수 → 결과 저장·표시
```

- 공통 SDK·LiteLLM 중계·제한 키·실호출은 구현 및 검증 기록이 있음.
- Shopshorts 관련 [PR #154](https://github.com/hhj4861/commerce-automation-kit/pull/154)와 [PR #156](https://github.com/hhj4861/commerce-automation-kit/pull/156)은 머지됨.
- #156의 공통 서비스 운영 배포 기록은 merge `7e9d8660fd60bfbcabd623cb66661f6dd100ae51`.
- 실계정 검증 후 Shopshorts discovery 활성화 설정은 원복했음. 서비스 배포와 일반 사용자 경로 활성화는 다른 상태임.
- Hanmadi v10은 배포·실모델·격리 저장 검증 기록이 있지만, 새 실제 영상의 운영 API→Redis 저장 전체 검증과 구분해야 함.
- Festa의 마지막 확인 기록은 shadow이며 실제 판단 채택(on) 완료 증거는 없음.
- 블로그·Replay 및 나머지 적용 후보의 완료 여부는 각각 확인해야 함.

위 내용은 마지막 기록 기준이며 현재 운영 상태를 새로 확인한 것으로 취급하지 마.

## 4. 집중 리뷰할 실제 실패 사례

### Shopshorts A — 일반 한국어 입력

에펠탑 추천에서 원문 대상명을 유지하고 별도 `searchQuery`를 생성하도록 개선했지만, 긴 프랑스어 검색어가 무관한 검색 결과를 반환해 후보 생성 단계에서 보류됐어. 이 요청은 JEV까지 도달하지 않았어.

### Shopshorts B — 공식 사이트·재료 질문으로 한정한 입력

- 질문: “에펠탑의 금속 재료는 무엇일까?”
- 답: 공식 발췌의 `puddle iron(퍼들 철)`
- JEV는 답의 근거를 pass로 판단했어.
- 방향·가상 예상·위치·도입 화면·질문·제목·의미 설명 등은 저신뢰 또는 불확실 판정으로 보류됐어.
- Codex 재검수는 위치 외 항목을 해소했지만, 초안의 `location`이 “정확한 위치가 확인되지 않음”이라 최종 보류됐어.

이는 실제 호출·재검수·화면 차단 경로의 검증이지, 정상 추천 성공이나 JEV의 일반 정확도 입증은 아니야. 위치 필드의 미충족과 전체 검색 자료에 위치 단서가 전혀 없다는 주장을 혼동하지 말고 실제 근거 묶음을 확인해줘.

다음을 독립적으로 검토해줘.

- 검색 실패, 근거 선택 실패, 초안 작성 실패, 검수 기준 오류를 분리할 수 있는가?
- 생성 프롬프트가 위치 미확인 기재를 허용하면서 검수는 실제 위치를 필수로 요구하는 모순이 있는가?
- 자료 묶음의 근거를 필드별로 충분히 활용하는가?
- 위치 필수 정책은 제품 요구상 타당한가? 변경한다면 어떤 범위·호환성이 필요한가?
- 사실을 포함한 연출 제안과 순수한 창작 제안을 올바르게 구분하는가?
- 재검수가 잘못된 사실을 통과시키거나 JEV의 확정 거절을 뒤집는 경로는 없는가?

임계값을 낮추거나 필수 검사를 제거해 통과시키는 것을 기본 해결책으로 삼지 마.

### Festa — 저신뢰 복귀 이후의 조기 종료

과거 JEV가 필요한 후속 질문 대신 추천 진행을 선택했으나 저신뢰로 채택되지 않았고, 기존 LLM도 잘못 종료한 사례가 있었어. 해당 기록·코드·회귀 테스트를 찾아 확인하고, JEV 저신뢰 복귀 이후에도 필수 정보 누락·조기 종료를 막는지 검토해줘. 이 사례만으로 JEV 전체 성능을 단정하지 마.

## 5. 품질·안정성·효과 검토

- `confidence`, 선택 확률, `margin`의 의미와 채택 기준이 적절한가?
- `pass/reject/uncertain/not_applicable` 집계와 필수 필드 처리가 일관적인가?
- 근거 ID·인용 검증, 대상 혼동, 상충 출처, 숨은 사실 전제를 처리하는가?
- timeout·취소·예산 초과·잘못된 응답·재시작·중복 요청에서 안전하게 종료하는가?
- 사용자 격리, 전용 키 권한, 로그의 민감정보 처리가 적절한가?
- rubric 버전 고정과 구버전 요청 재개가 보장되는가?
- 소수의 합성 사례·작성자 잠정 라벨·상관된 문항을 정확도 증거로 과대평가하지 않았는가?
- 잘못된 통과뿐 아니라 정상 후보의 불필요한 보류도 측정하는가?
- JEV 사용/미사용의 전체 품질·호출 수·비용·지연을 같은 조건으로 비교했는가?

## 6. 원하는 리뷰 결과

먼저 전체 결론과 가장 먼저 고칠 3가지를 제시해줘.

그다음 아래 결과를 정리해줘.

1. 플랫폼별 상태표: 구현 / 머지 / 배포 / 활성화 / 실호출 / 업무 품질 검증.
2. 발견 사항: 심각도, 파일·줄 또는 고정 리비전, 발생 조건, 사용자 영향, 수정 방향, 필요한 테스트.
3. 기존 계획 대비 누락·완료됐는데 남아 있는 항목·근거 부족 항목.
4. 추가 평가안: 독립 정답, 정상/오류/보류 사례, 오통과·오차단·보류율, 비용·지연 측정 방법.
5. 보완 순서: 운영 채택 전 필수 / 효과 검증 후 개선 / 후순위 확대.

확인된 결함, 설계 제안, 미확인을 명확히 구분해줘. 코드에 없는 문제를 추정으로 확정하거나 테스트 통과를 모델 품질 통과로 표현하지 마.
