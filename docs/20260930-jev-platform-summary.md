**사용자 방향: 문맥·의미를 해석하는 판단에는 가급적 Jev를 사용한다.** 중복, 관련성, 의도·상태, 후보 선택, 근거 일치, 학습 적합성은 Jev를 기본 설계 후보로 둔다. 생성 전에 방향·필요 정보를 먼저 판단하고, 생성 결과에서만 알 수 있는 오류는 필요한 단계에서 검사한다. 모든 후보의 운영 활성화가 완료됐다는 뜻은 아니다.

## 공통 적용 원칙과 완료 조건

- 연결 구조: **앱 서버의 어댑터 → 기존 LiteLLM → TypeSafe Jev**. JS/TS는 `@cak/litellm-client/jev`; Python은 같은 HTTP 계약의 어댑터. 별도 Jev 서버는 기본안이 아니다.
- 기능마다 입력 범위·선택지·판정 기준·rubric 버전·성공 기준을 먼저 정의한다. 후보가 없거나 근거가 부족하면 판단을 강제하지 않는다. 공유 상태로 판단할 항목은 가능한 한 묶되, 불필요한 사전·사후 중복 호출은 피한다.
- 품질·비용 비교를 거쳐 off→shadow→on으로 확대한다. confidence를 정답률로 간주하거나 전 기능에 같은 임계값을 적용하지 않는다. 호출이 없는 기능에 추가하면 비용 증가로 기록한다.
- 평가할 지표: 정상 후보 오차단, 잘못된 통과, 조기 종료·반복 질문, 검수자 일치도, 전체 성공률, p50/p95 지연, 복귀율, Jev+생성+재시도 총비용. 기존 계획의 100~200건은 초기 탐색 제안이며 완료된 검증 수나 현재 유료 호출 승인이 아니다.
- 날짜·금액·쿼터·진도·중복 ID·권한·상태 전이는 코드로 유지한다. 질문·번역·영상·음성 생성은 기존 생성 모델, 게시·사용권·동의의 최종 승인은 사람/기존 정책이 담당한다. Jev는 의미 판단을 보조하며 이 규칙을 무효화하지 않는다.
- 앱별 제한 키·예산·시간 제한·복귀 경로를 유지한다. 실패를 승인/중복 아님으로 바꾸거나 다른 키로 우회하지 않는다. 새 키·유료 평가 예산·운영 채택·PR 머지는 기존 승인 경계를 따른다.
