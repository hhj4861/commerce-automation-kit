# JEV discovery v2.2 — 필드 입력 분리 및 비사실 문구 처리

작성: 2026-10-04. 구현 기준: main `f4ff5c9`(PR #137). 작업 브랜치: `fix/jev-discovery-field-context`.

## 결론과 적용 범위

이 변경은 정상 후보 과보류의 원인 후보인 다른 필드의 간섭과 사실·연출의 혼동을 줄이기 위한 구현이다. 로컬 회귀 검증 결과는 아래에 기록한다. **실제 모델의 과보류 개선, 비용 절감 또는 운영 적용 완료를 뜻하지 않는다.** 운영 배포·클라이언트 활성화·새 유료 호출·키 발급은 이번 작업에 포함하지 않았다.

이전 v2.1 고정 3건 실호출은 정상 held / 근거 부족 held / 명백한 모순 rejected였다. 정상 건은 support 9개 중 8개가 기존 신뢰 기준에 미달했다. answer만 달라졌는데 entity 검사도 pass .62 → pass .19 → reject .43으로 달라졌다. 입력 간섭 가능성을 보여주지만 원인이나 전체 성능을 단정할 수 없다. 기존 원본 결과는 별도 프로젝트 브랜치 커밋 `a331444`의 `docs/qa/20261004-jev-v21-live-results.json`에 보존돼 있다.

## 구현

1. 새 research-v2 요청은 rubric `discovery-v2.2`로 고정한다. 공유 state에는 중복 제거한 evidence만 넣는다. 필드 검사마다 structured instructions에 해당 필드 전문, 역할, 참조용 entity만 넣는다. entity는 증거로 취급하지 않는다. 다른 필드·사용자 요청·이전 후보는 support 질문에 들어가지 않는다. 의미가 모호한 대명사는 근거 없이 보완하지 않고 보류 대상이다.
2. 제목·질문·기대 답변·시사점·연출·첫 장면의 문구 전체에 사실 주장이나 전제가 없을 때만 `not_applicable`을 허용한다. 이 선택도 confidence .8 / probability .8 / margin .2를 충족해야 한다. 대상·위치·실제 답변에는 이 선택지를 주지 않는다. 생성자가 준 부분 주장 목록이나 단어 매칭으로 검사를 생략하지 않는다.
3. “속삭임을 전달하도록 설계된 지붕을 보여주는 연출”은 설계 주장을 포함한다. “왜 이 지붕은 속삭임을 전달할까?”도 전제를 포함한다. 질문·가정·연출이라는 형식만으로 면제하지 않도록 질문을 정의하고, 전체 문자열 보존을 코드로 검증했다. 실제 JEV가 이런 혼합 문장을 올바르게 판별하는지는 아직 미검증이다.
4. relevance/value/duplicate는 각 질문 안에 자신이 필요한 후보 문맥을 둔다. 후보당 11문항(이력 있으면 12), JEV 1회, 기존 최대 3회·시간 제한을 유지한다. SDK·클라이언트 생성 계약·DB 스키마는 변경하지 않는다. 근거 원본 및 aliases는 결과에 보존한다.
5. `checks`에는 원래 선택지와 확률을 저장한다. 신뢰할 수 있는 reject 우선, 불확실·응답 오류 보류, 통과 후보만 이력 반영 규칙을 유지한다. v2.1 진행 중 요청은 원래 문맥·3선택지·rubric을 사용한다. v1.1/v2/v1.2 및 완료 재호출은 기존 동작을 유지한다.

설계 근거: [TypeSafe 공식 primitives 문서](https://docs.typesafe.ai/primitives) — 질문별 독립 평가, 구조화한 instructions, 공통 state를 사용하는 질문의 배치. 서버가 전달하는 문맥을 검증한 것이며 공급자 내부 처리까지 관찰했다는 뜻은 아니다.

## 검증

- Python 회귀: **49개 통과**, 프로세스 exit 0.
- JavaScript HTTP 소비자·Shopshorts·공통 SDK: **42개 통과**, 프로세스 exit 0. 합계 91개.
- 실제 로컬 HTTP → Python 서비스, Node bridge → 공통 SDK → 합성 공급자 HTTP를 포함한다. 검색·생성과 공급자 판단은 fixture이다.
- 단일 필드 변경 시 다른 support 질문과 공통 state가 불변임을 검사한다. entity는 명시적 참조 anchor이므로 변경 시 다른 검사에도 반영한다.
- 비사실 고신뢰 결과의 저장·새 Store 재조회·completion 재호출, 낮은 신뢰/확률 보류, 누락/NaN/bool/추가 선택지/불법 `not_applicable` 응답 거부, 불확실·모순 우선순위, v2.1 재개 호환을 검사한다.
- 한 요청의 최대 검색 4 / 생성 2 / JEV 3 회, 중복 요청 재과금 방지, 다른 lead 근거 차용 차단, 사용자 범위 분리 회귀를 유지한다.
- 로그 저장 위치: 사용자 지정 iCloud `gpt 작업/commerce-automation-kit/jev-field-context-20261004/`. 인증정보를 저장하지 않는다.

## 다음 품질 평가 — 아직 실행하지 않음

첫 단계는 기존 정상/부족/모순 3건의 입력·근거를 그대로 고정하고 v2.2를 실제 호출하는 것이다. 정상은 accepted, 부족은 held, 모순은 rejected여야 하며 실제 선택·confidence·확률·입출력 토큰·요금·지연을 모두 남긴다. 운영 클라이언트는 계속 비활성으로 둔다.

그다음 순수 질문/연출, 사실과 연출이 섞인 문장, 거짓 전제를 가진 질문, 명시적 가정, 모호한 참조, 상충 출처, 비즈니스 대안 사례를 추가한다. 실행 전에 독립 검토자가 라벨과 근거를 확정한다. 의도적으로 틀린 문장은 테스트 전용이며 콘텐츠로 발행하지 않는다.

JEV의 **순효과**는 아직 검증하지 않았다. 동일 입력·근거·생성 모델·예산을 고정한 JEV 미사용(기존 LLM 판단) 경로와 JEV 사용 경로를 비교해야 한다. 정상 통과율, 잘못된 통과율, 불필요한 보류율, 추가/절약된 생성 호출 수, 총비용, 전체 지연 p50/p95, 타임아웃을 분리 보고한다. 평가 순서와 입력을 사전에 고정하고 유리한 사례만 골라 재시도하지 않는다. 요청별 과금 한도와 호출 수를 정한 후 실행한다.

4선택지의 confidence는 기존 3선택지와 분포가 달라질 수 있다. 같은 수치 기준을 유지했다고 동일한 보정 정확도를 가정하지 않는다. 질문별 문맥 반복으로 입력 토큰이 증가할 수 있으며, 호출 횟수 유지가 비용 감소를 뜻하지 않는다. 현재 실호출 3건만으로 통계적 품질·ROI·p95를 결론내리지 않는다.
