# 알림함 속도·동시성 검증 — 2026-09-20

현재 단일 서버에서 전달·계정별 읽음 처리의 정합성은 시험 범위 내 통과했다. 개선 우선순위는 **Cloudflare 순차 발행을 배치/제한된 병렬 발행으로 개선**, 이어서 **전체 알림을 훑는 안 읽음 수 집계 개선**이다. 이번 작업은 검증과 결과 문서화이며 운영 코드·설정은 변경하지 않았다.

## 범위와 방법

- 코드 기준 `d0373ca`. 검증 중 HEAD가 `9bc5e90`으로 이동했으나 차이는 credential-broker README뿐이며 알림 구현은 동일했다.
- macOS arm64, Node v20.19.3. 부하 발생기와 로컬 서버가 같은 기기에서 실행됐다. 클라우드 배포/외부 인터넷 사용자/장시간 지속 부하의 성능 보증은 아니다.
- 운영 5198 서버는 인증 GET 10회만 조회. 알림 0건, `transport=cloudflare`, `warning=null`, pending/inflight/dead 모두 0. p50 1.18ms, p95 33.31ms(첫 연결 포함). 빈 알림함 결과이므로 대용량 성능 근거로 쓰지 않는다.
- 별도 임시 서버·DB에서 합성 알림 10,000/100,000건을 트랜잭션으로 미리 채움. JWT 사용자 인증, 실제 `/api/notifications` 응답 JSON 수신 완료까지 측정. 조회 결과는 페이지 크기 50이며 안 읽음 수 집계도 포함한다.
- 최초 연결 부하: 각 동시성 1/10/50/100에서 300요청. 재측정: 각 단계에서 100요청 예열 뒤 1,000요청. 응답을 받으면 다음 요청을 보내는 closed-loop 방식이며 동시 요청 수는 동시 사용자 수와 같지 않다. 여러 차례 장시간 반복한 통계가 아니다.
- 별도 Cloudflare 기본 큐/DLQ를 생성하고 실제 합성 이벤트 총 80건 사용. 기존 운영 큐는 소비·발행하지 않았다. 실험 후 두 임시 큐 모두 삭제 확인.
- 알림 회귀 테스트 `node --test apps/shopshorts/test/notifications*.test.mjs`: 23/23 통과. 인증/읽음 상태/재시작/재시도/ack 유실/만료 임대/중복 방지/계정 격리 포함. 장애 주입의 원격 API는 테스트용 응답이며 실제 Cloudflare 장애를 일으키지는 않았다.

## 조회 API: 예열 후 측정

p95는 측정 요청의 95%가 해당 시간 이내 완료됐다는 뜻이다. 각 행 1,000요청.

| 알림 수 | 동시 요청 | p50(ms) | p95(ms) | 처리량(req/s) | 오류 |
|---:|---:|---:|---:|---:|---:|
| 10,000 | 1 | 1.39 | 2.19 | 670.8 | 0 |
| 10,000 | 10 | 8.19 | 9.42 | 1205.1 | 0 |
| 10,000 | 50 | 40.34 | 43.28 | 1230.4 | 0 |
| 10,000 | 100 | 81.00 | 83.33 | 1233.4 | 0 |
| 100,000 | 1 | 6.18 | 8.67 | 154.4 | 0 |
| 100,000 | 10 | 54.82 | 69.82 | 174.7 | 0 |
| 100,000 | 50 | 264.67 | 297.44 | 185.2 | 0 |
| 100,000 | 100 | 527.61 | 651.90 | 183.4 | 0 |

첫 연결을 포함한 300요청 시험에서는 10만 건/동시 50~100의 p95가 1.58~1.64초였다. 예열 후에는 0.30~0.65초로 줄었으므로 연결 초기 비용과 짧은 부하 구간의 영향을 구분해야 한다. 최종 판단에는 두 결과를 함께 사용한다.

조회·읽음 변경 50:50 혼합 500요청, 동시 50:

| 알림 수 | p95(ms) | 처리량(req/s) | HTTP 오류 |
|---:|---:|---:|---:|
| 10,000 | 67.62 | 883.9 | 0 |
| 100,000 | 424.19 | 144.2 | 0 |

250개의 읽음 변경 후 정확히 250건 감소했고 다른 계정의 안 읽음 수는 변하지 않았다. `모두 읽음`과 동시에 조회 100회(동시 20)를 실행한 시험에서는 10만 건 조회 p95가 1,030.83ms였다. 전체 혼합 구간 3.57초는 모두 읽음 POST 하나의 지연 시간이 아니다. 대량 읽음 기록이 있는 상태의 집계 비용도 포함한다.

## SQLite 동시성

8개 실제 Worker Thread, 각각 독립 SQLite 연결을 같은 WAL DB에 열고 시작 장벽 후 동시에 실행했다. 생산자 시험과 소비자 시험은 순서대로 실행했으므로 생산·소비가 동시에 섞인 지속 부하 시험은 아니다.

- 삽입 시도 2,800회: worker별 고유 250건 × 8 + 공통 ID 100건 × 8.
- 기대 고유 이벤트 2,100건, 실제 알림 저장 2,100건, 남은 큐 0건.
- 소비자 8개 동시 처리에서 중복 선점 0, 오류/SQLITE_BUSY 0, 누락 0.
- 재측정 생산 구간 466.66ms, 소비 구간 928.36ms. 스레드 시작/동기화 비용 포함.
- 처리 분포는 180/190/530/190/420/410/10/170건으로 균등하지 않았다. 이 시험은 정합성 근거이며 공정한 분배나 무제한 쓰기 확장 근거는 아니다.

## 실제 Cloudflare 큐 전달

각 시험 시작 시 이벤트 40건을 한 번에 outbox에 넣고, 현재 서버와 같은 3초 interval 및 겹침 방지로 실제 `notificationTransport.tick()`을 호출했다. 첫 실행까지 3초를 포함한다. 알림함 INSERT 직후를 도착 시간으로 측정했으므로 브라우저 갱신 대기 시간은 포함하지 않는다.

| 처리 루프 | 이벤트 수 | 최종 저장 | 총 소요 | 도착 p50 | 도착 p95 | 전체 처리량 | 누락/중복 전달/오류 |
|---|---:|---:|---:|---:|---:|---:|---|
| 1개(현재 구조) | 40 | 40 | 12.25초 | 7.77초 | 12.11초 | 3.27건/초 | 0 / 0 / 0 |
| 2개(격리 실험) | 40 | 40 | 6.45초 | 5.97초 | 5.97초 | 6.20건/초 | 0 / 0 / 0 |

2개 루프는 같은 프로세스의 별도 SQLite 연결로 **같은 파일**을 공유했다. 각 루프가 발행과 소비를 모두 수행하므로 소비자만 늘린 실험이 아니다. 두 루프에서 HTTP 전송은 겹치지만 SQLite 실제 병렬 접근의 근거는 앞의 8개 스레드 시험이다. 1회 비교이고 API 연결/네트워크 지연도 다르므로 일정한 1.9배 개선을 보장하지 않는다.

Cloudflare 단건 발행 HTTP p50은 1루프 137ms, 2루프 132ms였다. 현재 구현은 20번의 HTTP 발행을 순서대로 기다린 뒤 pull을 시작한다. 1루프의 tick은 최대 5.75초로 3초 interval을 넘겼고, 서버의 실행 중 보호 때문에 겹치는 tick은 건너뛴다. **Cloudflare 서비스 자체의 한도가 아니라 앱의 발행 방식이 측정된 병목**이다.

두 시험 모두 마지막 로컬 pending/inflight/dead 0, 실제 알림 저장 수 40을 확인했다. 총 80건 규모의 단기 시험이므로 플랫폼 최대 처리량·장기 안정성·드문 재전달 빈도는 검증하지 않았다.

## 개선 우선순위와 운영 판단

1. 원격 발행을 배치 API 또는 동시 4~8개 정도의 제한된 병렬 발행으로 바꾸고, 수신이 발행 전체를 기다리지 않도록 분리하는 개선이 우선이다. batch의 부분 실패/접수 확인 후 outbox 보관/이벤트 ID 멱등성은 유지해야 한다. 이는 다음 구현 제안이며 적용하지 않았다.
2. `unreadCount`는 매 조회마다 알림 전체 인덱스를 순회하고 사용자별 읽음 인덱스를 조회한다. EXPLAIN은 `SCAN n USING COVERING INDEX sqlite_autoindex_notifications_1` + `CORRELATED SCALAR SUBQUERY` + 읽음 PK 조회를 보여줬다. 읽음 PK 인덱스는 이미 있다. 별도의 수 집계/읽음 기준점 설계를 통해 총 이력에 비례하는 반복 작업을 줄이는 편이 타당하다.
3. 현재 작은 운영 규모에는 사용할 수 있지만, 대량 이벤트의 수초 지연과 10만 건 이후 동시 조회 지연이 존재한다. 여러 서버가 각각 별도 SQLite 파일로 같은 큐를 소비하는 구성은 알림 이력을 분산시키므로 이 검증을 근거로 서버 수만 늘리면 안 된다. 다중 호스트 운영은 공용 영구 알림 저장소가 선행돼야 한다.

이번에 만든 테스트 서버/임시 DB는 종료·삭제했고 Cloudflare 임시 큐도 삭제했다. 5198 서버 재시작, 운영 데이터 변경, 소비자 증설은 수행하지 않았다. 원본 수치는 [JSON 측정 결과](20260920-notification-performance.json)에 함께 저장했다.
