# Hanmadi JEV v5 실호출 평가 도구 보완

상태: 구현 및 오프라인 검증 완료. 이 변경의 실제 유료 호출·운영 배포·PR 머지는 수행하지 않았다.

## 문제

PR #114의 v5는 품질 평가와 같은 배치 후보 간 중복 비교로 영상당 최대 2회 호출한다. 기존 `video-jev-live-check.mjs`는 두 배치를 합쳐 2회만 호출한다고 가정했고, 마지막 응답의 `unitN`을 읽었다. 2차 `pairN_M` 응답이 오면 품질 응답을 덮어쓰고 평가 결과를 읽지 못했다. 추가 요청을 차단할 때에도 먼저 카운터를 증가시켜 실제 전송 수보다 크게 보고했다.

## 변경

- 실제 `judgeVideo`와 SDK 검증을 그대로 사용한다. 앱 판정 기준·프롬프트·게시 흐름·운영 키는 변경하지 않았다.
- 명령줄에 `--live --max-requests N`(1~4)을 명시해야 한다. 원래의 2회 한도를 조용히 4회로 늘리지 않는다. 상한 검사는 전송 전이며, 실패 후 다음 배치·자동 재시도는 없다.
- 요청마다 배치·quality/dedupe 단계·질문 수·HTTP 상태·지연·사용량을 기록한다. 입력/출력 토큰은 모든 실제 호출을 합산한다. 실패/불명 사용량은 `unknownRequests`로 남기며 무료로 계산하지 않는다. 금액 상한은 별도의 제한 키 정책으로 관리해야 하며 이 스크립트가 달러 비용을 보장하지 않는다.
- 원 품질 판정은 SDK 검증 후 `judgment.evaluation`에서 읽는다. 최종 판정·검토 상태·비교 원답·비교 모델을 함께 보존한다. 품질 응답과 중복 응답을 혼동하지 않는다.
- 완료 사례, 실패 배치의 사례, 미시도 사례, 잘못된 자동 채택, 기대 채택 미충족, 검토/제외 수를 분리한다. 일부만 평가하거나 정상 후보가 저신뢰 검토대기로 남으면 전체 성공으로 보고하지 않는다.
- 관찰용 응답 사본은 1 MiB와 기존 요청 deadline 내에서 토큰 수만 읽는다. 키·제공자 오류 본문·요청 원문은 결과에 기록하지 않는다.

## 실행

앱 전용 제한 키와 gateway URL을 서버의 승인된 비밀 저장소에서 환경변수 `HANMADI_JEV_API_KEY`, `LITELLM_BASE_URL`로 주입한다. 키를 명령 인자·문서·로그에 쓰지 않는다. 키 발급·회수는 이 도구가 하지 않는다.

```sh
cd apps/hanmadi
node --import tsx scripts/video-jev-live-check.mjs --live --max-requests 4
```

이 명령은 실제 유료 요청을 수행한다. 두 합성 배치, 9개 사례이며 각 배치 최대 2요청, 전체 최대 4요청이다. 실제 중복 비교 대상이 없으면 더 적게 호출한다. 1~3의 낮은 상한도 허용하되 상한 도달은 불완전 평가/실패(exit 1)로 보고한다. 요청별 deadline은 앱의 12초다. 운영 키의 RPM/예산 제한을 우회하거나 다른 키로 복귀하지 않는다.

출력은 앱의 관찰 이벤트들과 마지막 `hanmadi_jev_synthetic_check` JSON이다. 최종 `passed`, `complete`, `metrics`, `usage`, `requestObservations`, `observations`를 확인한다. 출력/테스트 로그는 지정된 iCloud 작업 폴더에 저장한다.

`expectedAccepted`는 기존 합성 스모크 사례의 기대 채택 여부다. 독립 전문가 정답이나 원시 분류 정확도가 아니며, 24개 골드의 새 실호출 평가를 대체하지 않는다. v4 24응답 정책 재생 결과와 새 v5 실호출 결과를 섞지 않는다.

## 남은 단계

이 도구 변경의 main 반영은 PR 승인 이후다. v5 운영 승격은 Hanmadi 담당 세션이 별도로 진행하며, 이 문서는 배포 완료 증거가 아니다. 새 v5 프롬프트의 실제 품질·비용·지연 평가는 제한 키와 명시된 호출 예산으로 별도 수행해야 한다. 전체 플랫폼 확대 계획의 Python 어댑터·블로그·Shopshorts 등의 적용까지 완료했다는 뜻이 아니다.
