  • 담당: 현재 Codex 단독. 이번 작업은 문서·구조도 작성과 읽기 전용 운영 확인이다. 실제 자료 생성·게시·학습 제출·유료 호출·설정 변경을 하지 않았다.

  • 완료 기준: 운영 어드민/소스 대응표, 42개 기능 추적, 콘텐츠/사용자/AI 학습 구조, 권한·데이터·상태·실패 복구·인수 시험을 연결한다.

4. 관리자 화면·행동 설계

4.1 영상 찾기: 공통 수집함

검색/URL 입력, 언어, 용도(스터디·음악·둘 다), 분석 preset을 받는다. 행마다 원본 링크, 수집 상태, 확보 자산(원문/가사/오디오), 분석/검수/게시 상태, 마지막 실패 이유를 보여준다. 제목 자동 분류는 제안이고 관리자 선택이 최종이다. 기존 목록의 video ID와 자료 ID를 연결해 재수집으로 새 과금·초안이 생기지 않게 한다.

항목 상세의 단계는 원본 확인 → 자료 확보 → 분석 → 학습 구성 → 검수 → 게시/확인이다. 이전 단계는 다시 볼 수 있고, 입력을 바꿨을 때 어떤 결과가 무효화되는지 표시한다. 실제 값이 없는 진행률을 95%로 꾸미지 않고 현재 단계·대기 사유·재개 버튼을 보여준다. 긴 작업은 메뉴 이동·새로고침 뒤 같은 job으로 돌아온다.

4.2 자료 만들기: 표현 편집에서 수업 구성으로

목록은 기존 초안/게시 필터에 원본·언어·레벨·수업 목표를 추가한다. 편집은 기본 정보, 근거 cue, 표현, 활동/문항, 정답/피드백, 게시 미리보기로 나눈다. 기존 수동 원문 생성도 유지한다. 생성된 내용은 수정 가능하고 수정하면 관련 평가를 다시 요구한다.

문항마다 무엇을 배울지, 학습자가 할 행동, 정답 또는 평가 방식, 어떤 원문/자체 예문에 근거하는지가 있어야 한다. 단어 설명 몇 개를 묶어 수업이 완성됐다고 처리하지 않는다. 기존 단일 표현 교재는 그대로 지원하고 새 lesson artifact가 있는 자료만 다단계 수업으로 연다.

4.3 번역 후보: 별도 입력 경로 유지

동의된 사용자 후보를 검토하고 개인정보·언어·중복을 확인해 관리자 교재로 전환한다. 출처를 source provenance에 연결하되 비공개 사용자 정보를 공개 자료에 넣지 않는다. 기존 코드처럼 사용자 기여 자료는 모델 추가 학습 dataset에서 제외한다. 모델 학습 허용 범위를 넓히려면 별도 설계·동의 변경이 필요하다.

4.4 음악 관리: 한 곡의 준비 상태를 끝까지 보여주기

곡 상세는 영상/녹음 버전 → 가사·자막 → 음원/분석(사용 가능 시) → 학습 단위 → 검수·게시로 구성한다. 전체 가사 timeline과 선정한 학습 단위 목록은 따로 둔다. 원곡과 cue를 미리 들으며 시간 보정하고, 뜻·읽기·어휘·문항을 검토한다.

기능별 상태는 원곡 재생 가능, 가사 준비, 학습 준비, 녹음 연습 가능, 음정/리듬 분석 준비로 나눈다. 자막 있음이라는 YouTube metadata와 자막 원문 확보를 구분한다. 소유 채널 연결, 사용 허용 파일, 외부 공급자 중 실제 가능한 입력을 안내한다. 가사가 없어도 허용된 공식 감상은 가능하며 학습 버튼은 준비 상태와 이유를 표시한다.

Pretender의 현재 시작점은 수집 metadata와 공식 영상 ID다. 다음 성공 기준은 실제 자막/가사 응답→녹음 버전 일치→cue 재생 확인→학습 자료 검수·게시→학습 앱에서 연습이다. 등록 폼 저장·테스트 fixture 통과를 이 성공 대신 사용하지 않는다.

4.5 앱 반영 확인·AI 진단

앱 반영 확인에는 검색 미리보기와 별도로 게시 수업/곡 바로가기, 게시 revision, 실계정 E2E 상태를 둔다. AI 진단은 공급자 설정 존재, 인증, 실제 source 확보, 모델 분석, 검색, 음성/재생을 분리한다. 진단이 비용을 발생시키면 읽기 확인과 실제 실행 버튼을 나누고 범위를 표시한다. 화면 접근만으로 모델/오디오 시험을 실행하지 않는다.

모든 화면은 저장/실패/대기 결과를 live region으로 알리고 키보드 탐색을 지원한다. 토큰 선택 버튼을 줄 재생 버튼 안에 중첩하지 않는다. 단축키는 입력 중에는 작동하지 않고 모바일에 동일한 버튼을 제공한다. 재생·검수 맥락을 잃는 전체 화면 재마운트를 피한다.

5. 사용자 학습 구조

5.1 교과 구조와 학습 단위

기존 언어 EN/JA/TH/ES, 레벨 1~4, 상황 분류를 유지한다. 레벨을 공인 CEFR 등급이라고 바꾸지 않는다.

원문 cue와 학습 표현이 꼭 동일한 문장일 필요는 없다. 자체 연습 표현은 paraphrase/authored로 표시하고 원곡 가사처럼 보여주지 않는다. JA·TH 읽기와 뜻, 노래의 시적 표현/일상 사용 차이는 별도로 검수한다. cue 전체를 띄어쓰기만으로 단어로 나누지 않는다.

5.2 스터디 한 수업

  1. 목표·장면 확인 → 원본 해당 구간 듣기/보기.
  2. 이해 질문 → 뜻 공개·핵심 표현/문법 설명.
  3. 빈칸/순서/듣기 구분 등 목표와 맞는 활동.
  4. 따라 말하기 → 같은 의미의 다른 상황에서 말하기/튜터 대화.
  5. 수행 결과·다음 복습 확인. 원문과 다른 예문은 자체 예문임을 표시.

재생 횟수, 수업 완료, 표현 숙련은 별도 상태다. 정답형 문항은 고정 정답/허용 변형으로 검사하고, 말하기 평가는 STT·내용·발음 근거를 구분한다. 단순 전사 일치를 발음 점수로 표시하지 않는다. 근거가 없거나 마이크를 거절하면 채점 불가/대체 활동으로 처리한다.

5.3 음악 한 곡

원곡 감상 → 선정 구간 듣기 → 가사/읽기/뜻 확인 → 어휘·빈칸 → 구간 반복 → 따라 부르기/내 녹음 듣기 → 일상 표현 응용·복습으로 구성한다. 감상은 전체 곡 단위, 학습은 검토한 구간 단위다. LR의 자동 정지·뜻 공개와 Migaku의 단어 선택·복습 연결을 기존 player/단어장에 적용한다.

listen은 연속 재생, practice는 cue 끝 정지·뜻 공개, shadow/sing은 설정된 구간·횟수·대기시간으로 반복한다. 실제 음원에 없는 느린 TTS를 원곡/멜로디로 대체하지 않는다. 단어별 시간이 없으면 줄 강조만 제공한다. 저신뢰 음정·리듬 결과는 숫자 점수 대신 확인 불가 사유와 재녹음을 안내한다.

5.4 진도·개인화·복습

기존 진도/표현 저장소를 원본으로 유지하고 새 activity 기록을 adapter로 연결한다. 사용자·언어·표현 의미별 known/learning 상태를 공유하되 노래별 문맥을 보존한다. 복습 일정은 기존 방식을 먼저 재사용하며 Migaku의 복습 알고리즘을 복제했다고 주장하지 않는다.

다음 학습은 사용자가 고른 언어/레벨과 미완료 목표·복습 예정 항목으로 제안한다. 학습 효과나 숙련을 근거 없이 수치화하지 않는다. 출처 변경/게시 취소 때 이전 진도는 보존하고 새 버전과의 호환 여부를 표시한다. 개인 녹음의 보관/삭제와 분석 서비스 전송 동의는 별도로 관리한다.

6. 학습 관리: 기존 4단계를 중심으로 연결

단계구현 기준검증/적용 조건
1. 자료 버전게시된 ContentDraft와 허용된 MusicUnit을 KnowledgeEntry adapter로 읽어 immutable snapshot 생성. 원문 전체가 아니라 검수된 표현·뜻·scope 포함source/artifact/rights revision/hash 일치. 기존 12버전·120표현 등 제한을 명시하고 무단 확대 안 함
2. 검색 품질기존 lexical 평가와 질문 CRUD 유지. 자료가 있어야/없어야 하는 질문, 언어·레벨·상황·음악 용도 범위를 시험기존 pass/total과 사례 결과 보존. 검색 적중을 답변/교육 품질로 오해하지 않음
3. 의미 검색기존 embedding/index/evaluate/enable 경로 재사용. 자료 버전과 model/config/case digest를 묶음연결 준비와 실제 평가 통과 후 활성화. 신규 index 생성은 바로 활성화하지 않음
4. 모델 추가 학습별도 권한 dataset→source/recording 단위 train/validation/test 분리→준비/비용 확인→제출→조회→독립 시험→검수→별칭 활성화원문/가사 이용 허용과 모델 학습 허용은 별개. test split은 학습 요청에서 제외. 준비/성공/활성화를 다른 상태로 표시

현행 LearningState.index는 단일 index다. 최초 음악 통합은 같은 snapshot 안에서 범위를 필터링하며, 복수 index가 필요할 때만 별도 선택 필드를 추가한다. 동시에 여러 index가 이미 활성화된다고 가정하지 않는다. 기존 필터(language/level/scene)를 약화하지 않고 domain/purpose/권한 필터를 추가한다.

모델 활성화는 현재처럼 학습 성공·분리 시험 검수·서버 모델 별칭 등록·앱 키의 모델 접근 확인을 요구한다. 사용자/언어별 적용 범위를 분명히 하고 기본 모델 복귀를 제공한다. 현재 추가 학습 검수는 메모/확인 기반이므로, v2에서는 평가 입력/결과/버전도 연결해 감사를 가능하게 한다. 이 자동 연결은 신규 기능이지 현행 검증 완료가 아니다.

원문 철회/만료는 source→artifact→게시→dataset→index→active model 관계를 따라 무효화한다. 이미 재학습한 가중치에서 특정 자료가 자동 삭제된다고 주장하지 않는다. 해당 모델을 비활성화하고 공급자 삭제·재학습 정책에 따라 별도 처리한다. 평가·관리자 수정·사용자 피드백은 검토 후보로 되돌리되 자동 게시/파인튜닝하지 않는다.

Supadata·Musixmatch·LyricFind의 내부 시스템을 자체 복제하는 것이 아니다. 수집 관리·검수·학습 엔진·플레이어·복습은 자체 구축하고, 원천 자료는 승인된 입력/공식 공급 경로와 교체 가능한 어댑터로 연결한다. 기존 공개 영상 모델 입력도 공급자의 지원·이용 범위를 확인한 경우에만 사용한다. 모델이 “봤다”고 답하는 것만으로 자막 원문 확보가 되지는 않는다.

상태 모델

  • 원본과 단계: collected → acquiring → source-ready → analyzing → generated → reviewing → ready.
  • 작업 예외: blocked(자료/권한/설정 필요), failed(실행 실패), cancelled. 마지막 성공 단계·reasonCode·재개 조건 보존.
  • 게시 상태는 별도: draft / published / unpublished. 위 ready가 자동 게시를 뜻하지 않는다.
  • 음악은 embed-only, lyrics-ready, study-ready, pitch-ready capability를 독립적으로 표시한다. 가사 확보 실패가 공식 감상 기능을 없애지 않는다.
  • 기존 ContentDraft.status 등은 유지한다. 새 상태값을 기존 enum에 섞어 구 클라이언트를 깨지 않도록 job/capability 객체에 둔다.

API와 실행 위치

기존 /api/study/admin/videos의 prepare/status/process, /api/study/admin/music의 collection/save/generate/publish는 호환을 유지한다. 먼저 내부 공통 source/job 서비스를 만들고 기존 액션을 adapter로 연결한다. 이후 제안 /api/study/admin/media에 collect, set-purpose, acquire, analyze, review, publish, unpublish, retry, cancel을 단계적으로 추가한다. 모든 변경은 owner/origin 검사와 expectedRevision, 실행 요청 ID를 받는다. 작업 생성 응답은 job ID와 상태이고 긴 외부 작업을 HTTP 연결 하나에 매달지 않는다.

기존 앱·서버와 v2Driver의 CAS/claim을 우선 사용한다. 초기 구현은 영속 job과 제한된 단계 실행이면 충분하며 별도 이벤트버스/MSA는 만들지 않는다. 외부 비동기 작업은 provider job ID를 저장한다. 네트워크 응답 유실로 외부 실행 여부가 불명확하면 execution-unknown으로 남기고, 공급자의 idempotency/조회 지원 확인 전 생성 요청을 자동 반복하지 않는다. lease TTL·갱신·단계 제한 시간은 실제 함수 제한보다 짧게 설정해 검증한다.

선정한 공식 API에만 서버에서 접근한다. 키는 승인된 서버 비밀 설정에 보관하고 클라이언트·문서·iCloud 산출물에 넣지 않는다. 사용자 제공 오디오/녹음은 삭제·보관기간·외부 분석 동의를 분리한다. 모든 콘텐츠·cue·녹음을 Git에 저장하지 않는다.

6. 구현 묶음과 인수 시험

각 묶음은 관련 검증→자기 변경 커밋·push→PR 준비까지 진행하고, 실제 머지·운영 배포는 별도 승인 절차를 따른다. 아래 순서는 소요기간 약속이 아니다.

묶음포함 기능완료 산출물·검증
A: 수집·원문·작업 기반C01~C06, O02~O03통합 수집함, 기존 음악/영상 이관 adapter, 허용 원문 입력, job 재개·예산·CAS 시험. 외부 키 없이도 자체 자료로 통과
B: 스터디로 연결C07~C08, S01~S03·S05, O01실제 관찰 근거→수업/표현 생성→검토→게시→스터디/대화 검색. 기존 영상 파이프라인 회귀
C: 음악 학습 완성M01~M05·M09승인된 가사 cue·원곡 재생→자료 생성→검토→게시→곡별 학습. stable player·타이밍·원곡 청음 확인
D: 학습 UX·복습S04·S06, M06~M07, C09, O04문장 정지·뜻 공개·단어 선택·내 발화 재생·진도 복원. 접근성·모바일 확인
E: 실제 공급자 검증C04의 외부 어댑터이용 범위·키 준비 후 각 공급자 대상 곡 샘플 검사. Pretender는 실제 가사/녹음 매칭·학습까지 통과해야 성공
F: 멜로디 분석 고도화M08허가 오디오와 사용자 녹음의 음정/리듬 분석 평가. 준비 전 C의 원곡 감상·자막 학습 출시를 막지 않음

v2에서는 위 묶음 전에 기술 증거 확보(C10·M08: 실제 전사/가사 응답, 선율/리듬 후보 배포물 분석·자체 오디오 실측)를 둔다. A01~A04는 기존 메뉴 보존/연결에 포함하고, L01~L08은 별도 학습 관리 통합 묶음으로 검증한다. 전체 설계 §9 순서가 초기 묶음 순서보다 우선한다. 외부 준비가 필요한 실검증과 자체 자료로 가능한 구현을 구분해 진행한다.

반드시 실행할 E2E

  1. 스터디 × 네 언어: owner 검색/URL 수집→purpose/언어 확정→분석→근거·문항 검수→게시→검증용 학습자 수업→표현 저장→대화 적용→복습→다시 로그인해 진도 복원. 해당 자료가 게시된 정확한 revision인지 확인한다.
  2. 음악 × 네 언어: 원곡 수집→녹음 버전·자막/원문 연결→cue 미리보기→뜻/어휘 생성·검수→게시→음악 목록→원곡 소리·줄 이동·반복·뜻 공개→저장·복습→진도 복원. 자막 없는 영상은 embed-only 안내도 시험한다.
  3. 실제 외부 호출: 자체 제작/허용 영상의 실제 API 응답부터 시작한다. fixture 시험과 실제 공급자·브라우저 시험을 별도 기록한다. 상업곡은 제공 여부·이용 조건 확인 전 성공 수에 넣지 않는다.
  4. 실패/변경: 202 응답 후 재접속, 생성 응답 유실, 429, 무자막/다른 언어, source revision 변경 중 publish, 공급자 권한 만료·게시 취소, 같은 cue 저장 재시도, 삭제/임베드 불가 영상, 마이크 거절을 검증한다.
  5. 품질: 관리자도 원문 구간을 직접 재생해 분석과 비교한다. JEV 통과 수치만으로 실제 뜻/발음/가사 일치·원곡 재생을 통과 처리하지 않는다. 음정 점수는 별도 기준 음원 평가 전 노출하지 않는다.
