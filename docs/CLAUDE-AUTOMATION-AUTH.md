# Claude 연결 수정·코드 복사·영역별 추천 상태 — 2026-09-20

## Claude 신규 연결

운영 실패 기록은 `claude connect CLAUDE_AUTH_FAILED`였다. 기존 코드는 공식 `auth login --claudeai` 이후 새 프로세스의 `auth status`와 macOS 키체인 읽기에 의존한다. 격리된 가짜 파일로 실측한 CLI 2.1.278의 상태 형식은 정상(`loggedIn=true`, `authMethod=claude.ai`)이어서 필드명 문제라고 단정하지 않았다. 키체인 팝업 이후 실패의 정확한 OS 내부 원인은 기존 기록으로 확정할 수 없다.

사용자가 지정한 ddl-lint-engine의 구현과 [Claude 공식 자동화 인증](https://code.claude.com/docs/en/authentication#generate-a-long-lived-token)을 따라 신규 연결은 **`claude setup-token` → Cloudflare 암호화 저장 → 공식 CLI의 `CLAUDE_CODE_OAUTH_TOKEN` 주입** 경로를 사용한다. 이 경로는 `auth status`, 앱의 키체인 조회·삭제 명령, 로그인 자격 파일 가져오기를 호출하지 않는다. 개인 운영자 토큰을 상속하지 않고 해당 Google 사용자에게 연결된 토큰만 자식 프로세스에 전달한다.

사용자는 기존과 같이 공식 인증 화면에서 받은 일회용 코드를 웹 팝업에 붙여넣는다. 서버는 수정하지 않은 공식 CLI에만 코드를 전달하며, OAuth 엔드포인트·클라이언트 ID·교환 로직을 구현하지 않는다. PKCE URL 검증과 요청별 state 검증은 유지된다.

공식 문서상 setup-token은 1년짜리 토큰이며 refresh token 방식이 아니다. 앱은 발급 시각을 기록하지만 임의의 정확한 만료 시각을 만들어 표시하지 않는다. 만료·회수 시 재연결해야 한다. 기존 refresh-token 저장 형식은 이전 연결의 호환성을 위해 유지되며, 해당 계정은 해제 후 새 방식으로 연결할 수 있다.

공식 CLI의 터미널 출력을 PTY와 pyte로 복원해 성공 구간에서만 토큰을 추출한다. ANSI 제어문자를 단순 제거하면서 토큰 글자가 손실되는 것을 방지한다. CLI 출력은 로그나 HTTP 응답에 노출하지 않는다. 브리지의 stdout은 계정 워커 전용 비공개 파이프이며 터미널 로그에 연결하면 안 된다. 취소하면 해당 CLI 프로세스 그룹까지 종료한다.

최종 인증 저장소는 기존 Cloudflare 사용자별 암호화 vault다. 저장 실패에 대비한 임시 복구 파일만 격리 디렉터리(0700), 파일(0600)에 남긴다. 정상 저장 후 임시 디렉터리는 제거한다.

## 실행 환경 준비

공식 Claude CLI와 Python 3가 필요하다. 저장소 루트에서 실행한다.

```sh
npm run llm:setup -w @cak/app-shopshorts
```

설치 위치는 해당 체크아웃의 `node_modules/.claude-auth-venv`다. 저장소 외부에 설치한다면 `SHOPSHORTS_CLAUDE_PYTHON`을 해당 Python 실행 파일로 지정한다. `requirements-claude.txt`는 pyte와 wcwidth 버전을 고정한다. 운영 워커를 새 체크아웃으로 옮길 때 이 환경도 먼저 준비해야 한다. Pages에는 Python 설치가 필요 없다.

## 화면 변경

- Codex 인증 코드의 복사 버튼: 성공 표시, 클립보드 접근 거부 시 직접 복사 안내, 폴링 중 상태 유지.
- 주제·분위기 입력란 각각에 계정 확인/인증 대기 → 요청 대기 → 추천 생성 → 완료를 표시한다. 서버가 알려 준 대기·실행 상태를 사용하며 가상의 진행률이나 내부 추론을 만들지 않는다.
- 요청한 영역에만 생성 중 버튼과 경과 시간·취소 버튼이 표시된다. 실패·취소 안내도 해당 영역에 남고 입력 내용은 유지된다. 서버는 한 사용자당 한 요청을 처리하므로 다른 추천 버튼은 완료까지 비활성화하되 생성 중으로 표시하지 않는다.

## 검증과 반영 범위

- 실제 공식 CLI 2.1.278에서 새 setup-token 인증 URL 준비와 취소까지 확인했다. 사용자 동의·실제 구독 토큰 발급·실제 추천 생성 성공은 별도 재시도가 필요하다.
- Node 앱·브로커 테스트 147개 통과: 새 토큰 연결/추천 시 키체인 경로 미호출, 사용자 토큰 격리, 보관 실패 복구, 기존 토큰 갱신 호환성.
- Python 테스트 5개 통과: PTY에서 코드 제출과 완료 토큰 전달, 화면 재그리기 복원, 잘못된 state 거부, 토큰 조각/API 키/refresh token 거부, 자식 프로세스 취소.
- Chrome 통합 테스트 19개 검증 항목 통과: 실제 로컬 API·암호화 저장소·큐 워커와 연결해 코드 복사 및 클립보드 거부, 영역별 진행·취소·실패, 모바일 화면을 확인했다. 제공사 인증과 생성 결과는 fixture다.
- 작업 브랜치/PR 준비 단계이며, 새 PR의 머지·운영 반영 승인 전에는 운영 Pages·워커를 변경하지 않는다.
